# Consumer findings — numbers.ch on 0.9.0 (the D2 witness)

Date: 2026-08-13
Source: `numbers.ch` branch `feat/sankara-ui-heading-tokens`, bumped `^0.7.0` →
`^0.9.0`. Next 16.1.6 / Turbopack production build (`BUILD_DIST=.next-verify
MODE=preview`), served with `next start`, measured in Chrome at 1400px. Lint
clean, 43 tests green, 26 pages prerendered against draft CMS content, console
clean.

This round completed the two migrations the 2026-08-05 retrofit left open:
`Icon`/`IconBox`/`icon-data.ts` → `FaIcon`, and 28 bare `<hN>` → `Heading`.
Net **−304 lines** (icon layer alone: −315).

Unlike `next-storyblok-template`, this project renders `FaIcon` (65 on one page)
and carries a real legacy `.h1`–`.h3` scale. It renders **no** `Dialog`, **no**
`Popover` and **no** form primitive — see Unobserved.

## 1 — D2: the first real `.hN` collision, and it resolves by layer

Both previous rounds reported an empty collision census because the template has
no legacy heading scale. numbers.ch has one: own family, weight 800, own
clamps, letter-spacing, in `@layer components`. Census of the built stylesheet —
**8 `.hN` rules, and `.h1`/`.h2`/`.h3` are each defined twice**:

| Layer | Rule |
| --- | --- |
| `base` (package) | `.h1{font-size:var(--heading-1);line-height:1.1}` |
| `base` (package) | `.h2{font-size:var(--heading-2);line-height:1.15}` |
| `base` (package) | `.h3{font-size:var(--heading-3);line-height:1.2}` |
| `base` (package) | `.h4{font-size:var(--heading-4);line-height:1.3}` |
| `components` (consumer) | `.h1{font-family:…;letter-spacing:-.02em;margin:0;font-weight:800;line-height:1.06}` |
| `components` (consumer) | `.h2{…;letter-spacing:-.01em;font-weight:800;line-height:1.1}` |
| `components` (consumer) | `.h3{…;font-weight:700;line-height:1.1}` |
| `components` (consumer) | `.on-light .h2,.on-light .h1{color:…}` |

Layer offsets in the emitted sheet: `base` 8067, `components` 14079, `utilities`
29910. Both sides set `line-height`; the consumer wins on every shared property
by layer order alone. Measured on the served page:

| Element | Computed |
| --- | --- |
| `h1.h1` | 56px, Gabarito, 800, line-height **59.36px (1.06)**, letter-spacing −1.12px, margin 0 |
| `h2.h2` | 36px, Gabarito, 800, line-height **39.6px (1.1)**, margin 0 0 24px |

`1.06`/`1.1` are the consumer's values, not the package's `1.1`/`1.15`.
`font-size` is the package's, because the consumer's rules deliberately do not
set it — the 2026-08-05 round moved the scale into `--heading-N`. **The two rule
sets compose; they do not fight.** That is the design working as intended, on
the only project that could prove it.

**The caveat worth shipping in the README.** This composes cleanly *because* the
legacy scale sits in `@layer components`. A consumer who puts the same rules in
`@layer base` — the more obvious place for a type scale — lands in the same layer
as the package, and the winner falls to source order, i.e. to whether their
`@import` precedes their rules. numbers.ch is a favourable case, not a general
guarantee.

**`.h4` is a real trap, unhit here.** The package defines `.h4`; this consumer's
legacy scale stops at `.h3`. A `<Heading level={4}>` would therefore take the
package's `font-size`/`line-height` but none of the site's heading family or
weight — it would render at heading size in body font. numbers.ch uses only
levels 1–3, so nothing broke, but the next consumer with a 3-step scale will hit
this the first time an editor needs an `h4`.

## 2 — D3 verified in a shipped build, on the project the comment was written for

`Heading`'s source comment justifies always emitting the class by citing a
project that "defines `.hN` and no tag rule at all, where the class is the only
thing that renders a heading". numbers.ch **is** that project, and it is now
measured rather than reasoned about.

In the built HTML, with `visual === level` throughout: `<h1 class="h1 …">`,
`<h2 class="h2…">` ×47, `<h3 class="h3…">` ×6 — the class is emitted every time.
Injecting a classless `<h2>` into the same subtree of the served page:

| Element | Computed |
| --- | --- |
| `h2.h2` (what `Heading` emits) | 36px, Gabarito, 800 |
| `<h2>` appended, no class, same tree | **16px, Outfit, 400 — body copy** |

The template round had to *inject* a consumer bare-tag rule to manufacture this
hazard. Here it is the native state: bare heading tags are unstyled, so
`visual === level` emitting nothing would have silently rendered 67 headings as
body text. D3 is load-bearing, not defensive.

## 3 — `FaIcon` closes the CMS free-text gap; the census says so

The 2026-08-05 round deferred this migration because a `name → IconDefinition`
map cannot be exhaustive against free text. `FaIcon` removes the premise. Census
of **every** icon field in the space (CDA, draft *and* published, 20 stories):

- ~110 icon values, **all** `fa-*`.
- **Zero** `solar:*`, `ri:*`, or any other Iconify name — in either version.

So the 50-entry build-time SVG set (`icon-data.ts`, 255 lines, plus a 45-line
generator) was serving nothing but one brand fallback. Deleted:
`Icon.tsx` (61), `icon-data.ts` (255), `gen-icons.mjs` (45).

Migration notes for the README:

- **`FaIcon` has no `color` prop; the old local `Icon` did, and 20 of 37 call
  sites used it.** The webfont glyph inherits `currentColor`, so every one
  converted to either a Tailwind text utility (`text-primary-light`,
  `text-white/80`) or a `color` on the existing parent (`IconBox`). This is a
  better factoring, but it is a per-call-site edit, not a rename — worth one
  line in a migration note.
- `.sankara-fa-icon` *nominally* supplies what the old component's inline style
  did (`inline-flex`, `flex-shrink:0`, centring, `line-height:1`) — but under a
  FontAwesome kit only `flex-shrink` and `line-height` survive the cascade. See
  finding 5; this bullet is the trap, not the reassurance it first looks like.
- `size` maps 1:1. The local component defaulted to 24; `FaIcon` inherits font
  size when `size` is omitted. All 37 call sites passed an explicit size, so the
  difference never surfaced — but a project relying on that default would
  silently reflow.

## 4 — NEW: `FaIcon` + a subsetted kit fails silently, and the docstring doesn't warn

**The one real defect-shaped finding.** `FaIcon`'s `HAS_STYLE_PREFIX` correctly
passes `"fa-brands fa-linkedin-in"` through without prepending `fa-solid`. The
class list it emits is right. It still renders nothing.

The site's kit is a **Pro Plus 7.3.1** kit. Read from the live page's CSSOM:

```
@font-face families actually loaded: "Font Awesome 7 Pro", "FontAwesome"
.fa-brands / .fab font-family rules: none
.fa-linkedin-in glyph rules:         none
```

Solid, regular and light are *weights* of the single Pro family, so those all
resolve. **Brands is a separate font the kit does not serve.** Probing the
served page directly:

| Class | `::before` content |
| --- | --- |
| `fa-solid fa-bullseye` | `"" / ""` — glyph present |
| `fa-regular fa-laptop-code` | `"" / ""` — glyph present |
| `fa-brands fa-linkedin-in` | **`none`** |
| `fa-brands fa-instagram` | **`none`** |

Content has 7 `fa-brands fa-linkedin-in` values plus one code-authored footer
icon. All eight would have rendered as invisible 26px boxes — laying out
correctly, occupying space, throwing nothing. This is worse than a crash: the
element is present and sized, so it survives review.

Note this is a *deployment* property, not a `FaIcon` bug — but `FaIcon` is where
the consumer meets it, and its docstring says only "The consumer must load a
FontAwesome kit (or webfont CSS)". Two asks:

1. **Document the family axis.** One line: brands ships as a separate font;
   a kit that serves only the Pro/solid family renders `fa-brands` names blank
   with no error. That sentence would have saved this migration a round trip —
   I initially cleared brands as safe by reading the *published* `pro-plus.min.css`
   release file, which does contain the brands rules, before checking what the
   kit actually injects. The release CSS and the kit's subset are different
   artefacts, and only the second one matters.
2. Consider whether `FaIcon` can fail louder. It cannot detect a missing glyph
   (that is runtime CSS), so documentation is the only lever available — which
   is exactly why ask 1 is the whole of it.

numbers.ch's resolution: a 44-line `BrandIcon` that inlines the one brand mark
in use and delegates everything else to `FaIcon`. It replaces a 255-line table,
and it is deletable the day Brands is enabled on the kit.

## 5 — NEW: `.sankara-fa-icon` is inert against an unlayered FontAwesome kit

Caught only by a pixel diff against the pre-migration build, and the single
highest-value finding of this round.

`.sankara-fa-icon` lives in `@layer components` and declares
`display:inline-flex; align-items:center; justify-content:center;
flex-shrink:0; line-height:1`. A FontAwesome **kit injects fully unlayered
CSS** — `grep -c '@layer'` on the served kit stylesheet returns **0** — and
unlayered declarations outrank every layer. The kit's own rule sets:

```css
display: var(--fa-display, inline-block);
width:   var(--fa-width, 1.25em);
line-height: 1;
text-align: center;
```

So for any consumer loading a kit, `.sankara-fa-icon`'s `display` **never
applies**, the element is `inline-block` rather than a flex container, and its
`align-items`/`justify-content` are therefore inert. Measured consequence:
glyphs sit one to three pixels off-centre inside fixed-size boxes (`IconBox`,
orbit nodes) across every page. Pixel diff before the fix: 2,586 differing
pixels on `/framework`, 5,539 on `/`, 1,998 on `/lab/b2b-marketing-sales`.

The consumer fix is one unlayered, tag-qualified rule — `i.sankara-fa-icon`
`(0,1,1)` beats the kit's `(0,1,0)` on specificity rather than source order,
which matters because the kit injects its stylesheet at runtime:

```css
i.sankara-fa-icon { display: inline-flex; align-items: center; justify-content: center }
```

That took six of nine pages to a **byte-identical** rendering.

**Ask:** set `display`/centring on the element's `style` attribute in `FaIcon`,
the way this project's hand-rolled component did, or drop them from
`.sankara-fa-icon` and document that centring is the consumer's job under a
kit. An inline style is the only thing that reliably beats unlayered kit CSS,
and `FaIcon` already writes a `style` attribute when `size` is set. Shipping
declarations that a kit silently defeats is worse than not shipping them: the
class reads as if it handles centring.

Note this generalises beyond `FaIcon` — **any** package rule in `@layer
components` is defeated by any unlayered third-party stylesheet the consumer
loads. `FaIcon` is simply the one component guaranteed to sit next to one.

## 6 — Correction: the three Carousel gaps closed in 0.7.0, not 0.9.0

The 0.9.0 template observations (finding 5) credit 0.9.0 with closing all three
gaps from the 2026-08-05 retrofit. Verified against the npm 0.7.0 tarball:
`.sankara-carousel`, `--carousel-dot`/`--carousel-dot-active` and
`--carousel-per-view` are **all present in 0.7.0**. The template saw them
together only because it jumped 0.7.0 → 0.9.0.

numbers.ch deleted its three consumer bridges at 0.7.0 (commit `7c16a15`). What
0.9.0 adds on top is the inline-utility move. Re-measured on 0.9.0, unchanged:

| Assertion | Measured |
| --- | --- |
| Root | `flex`, `column`, gap 24px, `.sankara-carousel numbers-carousel numbers-carousel--onviolet` |
| Track | `flex`, gap 16px, `scroll-snap-type: x mandatory`, `overflow-x: auto` |
| Slide (`perView=3`) | `flex-basis: calc(33.3333% - 10.6667px)`, `shrink: 0`, `snap-align: start` |
| Dots | `flex`, centred, gap 8px |
| Violet-section dots | inactive `rgba(255,255,255,.4)` @10px, active `#fff` @32px |
| Responsive `perView` | `--carousel-per-view: 1.28` ≤768px, `1.14` ≤480px, plain media queries |
| Disclosure summary | `flex`, `space-between`, gap 16px, `list-style: none` |

Zero `!important` remain anywhere in the consumer's carousel CSS. Both 08-05
workarounds are gone and the rendering is identical.

## 7 — `className` overrides: the gain is real, the exposure is one class

The template reported "exposure: none". numbers.ch had exactly one: `shrink-0`,
passed alongside `transition-transform group-open:rotate-180` to the `FaIcon`
used as a `Disclosure` indicator in three sections. Under 0.9.0 it is redundant
— `.sankara-fa-icon` owns `flex-shrink: 0` in `@layer components` — and it was
dropped. One `style={{ flexShrink: 0 }}` was dropped for the same reason.

No `gap-*`/`flex` overrides, and **no `Dialog` anywhere in the project**, so
`.sankara-dialog-{sm,md,lg}` and the `m-*`/`w-*`/`max-h-*`/`overflow-*` override
path remain unexercised by this consumer too. Two consumers in, that surface
still has no witness.

## 8 — `@source` narrowing confirmed: 1,127 bytes, 14 classes, nothing lost

Applied the template's fix (`@source '…/core/dist/components'`) and A/B'd two
full production builds:

```
wide   @source '…/@sankara-ui/core'                    80,242 bytes
narrow @source '…/@sankara-ui/core/dist/components'    79,115 bytes
                                                       −1,127 (1.4%)
```

14 classes dropped, all traceable to README prose:

```
bg-surface  border-0  col-span-full  contents  group-open\:hidden  p-2
popover-open\:rotate-180  pt-4  rounded-card  rounded-none  shadow-raised
text-5xl  text-on-surface  w-72
```

Set difference the other way is **empty** — nothing appears in the narrow build
that the wide one lacked. Verified live that the one risky-looking casualty is
inert: `rounded-card` (which 0.7.0's `Carousel` emitted inline on dots) matches
zero elements, and dots keep an 18px radius from `.sankara-carousel-dot`.

Smaller than the template's 2,099 bytes because numbers.ch's own markup already
uses `border-t`, `py-5` and friends, so those survive on their own merit. The
delta is different per consumer; the fix is the same. **This is a second
independent vote for asks 1 and 2 of the template round's finding 6** — and note
the dropped set now includes package *token* names (`bg-surface`,
`shadow-raised`, `text-on-surface`, `rounded-card`), which read as real API in a
README and are the most tempting thing for a consumer to leave scanned.

## 9 — Pre-existing consumer bug the migration surfaced

`.arrow-link svg, .btn-arrow svg { transform: translateX(5px) }` on hover: the
selector only ever matched `<svg>`, but arrow icons have rendered as `<i>` since
long before this migration, so the nudge had been silently dead. Fixed
consumer-side by also matching `.sankara-fa-icon`.

Package-relevant only as a small endorsement: consumers *do* reach for icons by
element type, and a stable class hook is what makes that survivable.
`.sankara-fa-icon` existing is why the fix is one selector.

## 10 — What the pixel diff actually cost, and the one accepted change

Full-page screenshots (1400×7000, `--force-prefers-reduced-motion`) of nine
routes on both builds, diffed with ImageMagick. A control — the same build shot
twice — differs by **0** pixels, so the comparison is deterministic and every
non-zero result below is real.

| | before centring fix | after |
| --- | --- | --- |
| `/` | 5,539 | 1,562 |
| `/framework` | 2,586 | **0** |
| `/lab/b2b-marketing-sales` | 1,998 | **0** |
| `/lab/smarketing-playbook` | 1,961 | 1,494 |
| `/ueber-uns` | 1,962 | 165 |
| `/lab/case-study-desinfecta` | 1,273 | **0** |
| `/discovery-call`, `/impressum`, `/lab/overview` | 0 | **0** |

The residual is **one icon**, and it is a fix rather than a regression. In the
old build the HeroOrbit `fa-dollar-sign` computed **12.48px wide against an
inline `width:20px`** — the hand-rolled `<i>` had no `flex-shrink`, so a tight
flex row crushed it to 62% of its intended size. `.sankara-fa-icon` sets
`flex-shrink: 0`, so it now renders at 20px and the adjacent label shifts right.
That accounts for `/` and `/lab/smarketing-playbook`, the two routes with a hero
orbit. `/ueber-uns`'s 165 pixels form no cluster larger than 8px — isolated
antialiasing specks.

Site-wide there was exactly **one** such squashed icon; the other 14 zero-width
matches were elements inside `display:none` containers, not shrunk ones. So
`flex-shrink: 0` in the package silently repaired a latent consumer bug, and the
pixel diff is what turned "probably fine" into a counted result.

## Unobserved

Not measured, and not to be read as passing:

- **`Dialog`, `Popover`, `RichText`, form primitives.** None rendered by this
  project. Dialog size classes, drawers (`placement="end"`), the popover clamp
  and `id ?? name` remain untested here.
- **`Heading` levels 4–6.** Only 1–3 are used. The `.h4` gap in finding 1 is
  reasoned from the CSS, not rendered.
- **Nine utility-styled headings deliberately left as bare `<hN>`** (e.g.
  `<h2 className="font-heading text-3xl font-extrabold">`). Converting them
  would inject the legacy `.hN` cascade — its line-height, letter-spacing and
  margin — and change their rendering. They are one-offs with their own type,
  not part of the scale. Worth a README note: `Heading` adoption is not
  mechanical for headings that already carry a bespoke utility set.
- **Brands rendering after a kit change.** The `BrandIcon` workaround is
  verified (8 inline SVGs, 17×17, inheriting `currentColor`); enabling Brands on
  the kit is not.
- **Chrome only, 1400px only.** The responsive `perView` rules were confirmed
  present in the built CSS and by their computed effect at desktop width, but no
  narrow-viewport measurement pass was run this round.
- **`MODE=preview` / draft content only.** The published census matched draft on
  icon names, but the build itself read draft.
