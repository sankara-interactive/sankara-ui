# Consumer findings — next-storyblok-template on 0.9.0

Date: 2026-08-13
Source: `next-storyblok-template` branch `feat/sankara-ui-integration` (PR #34),
bumped `^0.7.0` → `^0.9.0`. Next 16.3.0 / Tailwind 4.3.3 / **Turbopack
production build**, served with `next start`, measured in Chrome 151 at 1400px
and 500px. `yarn check` green (97 tests). Console clean across the whole
interaction pass.

The template renders Carousel, Dialog, Disclosure, Popover, Button, Heading and
RichText from CMS-driven bloks. It renders **no** `FaIcon`, **no** `Icon`, **no**
form primitive and **no** `placement="end"` Dialog — see Unobserved.

## What 0.9.0 changed, from the consumer side

The four components that moved their defaults into `styles.css` emit exactly the
class hooks and nothing else now. Diffed against the 0.7.0 tarball:

| Component | 0.7.0 emitted | 0.9.0 emits |
| --- | --- | --- |
| Carousel root | `sankara-carousel flex flex-col gap-6` | `sankara-carousel` |
| Carousel track | `… relative flex snap-x snap-mandatory overflow-x-auto [scrollbar-width:none] [&::-webkit-scrollbar]:hidden` | `sankara-carousel-track` |
| Carousel slide | `… shrink-0 snap-start` | `sankara-carousel-slide` |
| Carousel dots | `flex justify-center gap-2` | `sankara-carousel-dots` |
| Disclosure summary | `flex cursor-pointer list-none items-center justify-between gap-4` | `sankara-disclosure-summary` |
| Disclosure indicator | `size-2.5 shrink-0 rotate-45 border-r-2 … group-open:rotate-[225deg]` | `sankara-disclosure-indicator` |
| Dialog | `sankara-dialog m-auto` + `SIZES[placement][size]` (`max-w-3xl`, `w-[min(36rem,95vw)]`, …) | `sankara-dialog` + `sankara-dialog-{sm,md,lg}` |

One inline utility survives in `dist`: `Icon` (`cn('inline-block shrink-0')`),
deliberately, per its own comment. That single holdout is what finding 6 is
about.

## 1 — Import order holds, now with a components layer in play

The last unobserved risk from the 0.6.0 round (`RichText` D3, `Heading` D4) had
only ever been satisfied by fixture construction. It survives a second real
build, and 0.9.0 raises the stakes: a mis-ordered import no longer costs
decoration, it costs layout.

Emitted layer order in the single built stylesheet, by byte offset — Lightning
CSS merges each layer to one block and drops the `@layer …;` statement, so
**first appearance is the order**:

```
0      @layer properties
1045   @layer theme
2876   @layer base
8873   @layer components
14691  @layer utilities
```

`components` before `utilities` is the whole mechanism behind finding 4.

Inside `@layer base`, 76 top-level rules in this order:

```
0–47   Tailwind preflight (…, h1–h6 reset at 5, ol/ul at 17, …)
48–68  package :where(.sankara-richtext) …
69–72  package .h1 .h2 .h3 .h4
73–75  template: p a, @media (hover:hover), :is(.h1…h6){font-weight:500}
```

Preflight → package → consumer, exactly as the contract requires, with the
template's own rules last. Inside `@layer components`, 48 rules, all the
package's: dialog (0–14), disclosure (15–22), popover (23–27), button (28–29),
form controls (30–39), carousel (40–46), fa-icon (47). The template contributes
none.

## 2 — `.h1`–`.h6` census clean; the bare-tag hazard reproduced in a shipped build

Census of the built CSS: exactly the package's four rules plus the template's
one deliberate `:is(.h1, …, .h6) { font-weight: 500 }`. No collision — same
result as the 0.6.0 round, and for the same reason: this template has no legacy
`.hN` scale. It remains a poor witness for D2.

The hazard itself is now measured **outside a fixture** for the first time. A
consumer bare-tag rule was injected into the served page — the strongest
position one can occupy, `@layer base` after the package import:

```css
@layer base { h2 { font-size: 48px } }
```

| Element | Computed |
| --- | --- |
| `h2.h2` (what `Heading` emits) | **30.82px** — unchanged |
| `<h2>` appended with no class, same tree | **48px** |

`(0,1,0)` beats `(0,0,1)`; the consumer's own heading CSS applies everywhere the
package's class is absent and loses everywhere it is present. The fixture
measured 36px vs 48px; a shipped build measures 30.82px vs 48px. Same shape,
different clamp. The Risks entry stands.

## 4 — `className` overrides now win, deterministically

Verified on the open dialog by injecting a rule into `@layer utilities` — the
layer a real Tailwind utility lands in — and adding the classes:

| | before | after `max-inline-size: 20rem` / `margin: 0` / `overflow-y: auto` |
| --- | --- | --- |
| width | 768px | **320px** |
| margin | `162px 316px` | **0px** |
| overflow-y | `visible` | **auto** |

This is the real improvement. In 0.7.0 the dialog's size and margin were
themselves utilities (`max-w-3xl`, `m-auto`), so a consumer's `max-w-sm`/`m-0`
tied them in `@layer utilities` and the winner fell out of Tailwind's internal
property sort — not out of anything the consumer could reason about. In 0.9.0
the package rule sits in `@layer components` and any consumer utility beats it
by layer order alone, with no specificity or source-order dependency.

**Template exposure: none.** No `className` is passed to Carousel, Disclosure,
Dialog or FaIcon anywhere in the template. Its one Dialog (`placement` default,
`size="lg"`) computes 768px — the same 48rem `max-w-3xl` gave in 0.7.0 — so the
rendering did not change. The gain is available, not yet drawn on.

## 5 — Carousel: all three numbers.ch gaps are closed, and observed

The 2026-08-05 retrofit findings listed responsive `perView`, tokenised dot
colours and a namespaced root class as the package's most-demanded gaps, each
bridged consumer-side. 0.9.0 closes all three, measured here:

- **Responsive `perView`, no `!important`.** The private `--_carousel-per-view`
  is inline on the root; the public name is read first. A plain media query
  moved the slide from 152px to 336px at a 500px viewport:

  ```css
  @media (max-width: 768px) {
    .sankara-carousel { --carousel-per-view: 1.2; --carousel-gap: 8px }
  }
  ```

  Track gap followed to 8px. The old bridge — `flex-basis: … !important` on
  `[aria-roledescription='slide']`, needed because 0.7.0 set flex-basis inline
  per slide — is no longer necessary.
- **Contextual dot retheme works.** Setting `--carousel-dot` /
  `--carousel-dot-active` on an ancestor recoloured inactive and active dots
  independently. This is what numbers.ch's violet section needed.
- **`.sankara-carousel` root class** exists and is the media-query hook above.

One trap, not a defect: `.sankara-carousel-dot` carries `transition: all 150ms`,
so a token change animates. A synchronous `getComputedStyle` right after the
change reads the *pre-change* colour (serialised in `oklab`, mid-interpolation).
Cost us one false-positive investigation; anything asserting dot colour must
await the transition.

## 6 — NEW: `@source` at the package root leaks README prose into consumer CSS

Tailwind v4 does not scan `node_modules`, so every consumer of this package is
told to add `@source`. Pointed at the package root — the obvious reading — it
scans `README.md` too, and Tailwind generates utilities for every class name
that appears in the documentation.

Measured in the template's built stylesheet: **2,099 bytes** (22,804 → 20,705,
9.2%) of utilities that no markup on the site uses:

```
.w-72  .text-5xl  .col-span-full  .font-extrabold  .bg-transparent  .border-0
.border-t  .outline  .ring  .p-0  .p-2  .pt-4  .py-5  .inline  .transition
.transition-transform  .group-open\:hidden  .group-open\:rotate-180
.popover-open\:rotate-180
```

Every one traced to `README.md` prose (`w-72` also appears inside a `styles.css`
comment). Before 0.9.0 this was noise on top of a directive that genuinely had
to be there; now the components need nothing from it, and `Icon`'s two inline
utilities are the only remaining reason it exists at all.

Template-side fix, applied:

```css
@source '../node_modules/@sankara-ui/core/dist/components';
```

`.inline-block` and `.shrink-0` survive (Icon keeps working for any project that
imports `@sankara-ui/core/icon`), everything above disappears, nothing else in
the emitted CSS changes.

**Two asks, either one resolves it:**

1. Document the narrow path in the README's install section. One line, and it
   stops every consumer from shipping the docs as CSS.
2. Better: move `Icon`'s `inline-block shrink-0` to a `.sankara-icon` rule in
   `styles.css`, or to an inline `style`, and `@source` stops being an install
   step at all. The current comment justifies keeping them inline because
   `./icon` consumers may never import `styles.css` — an inline `style`
   attribute honours that constraint without asking anyone to scan
   `node_modules`.

## 7 — Form primitives ship as CSS but are unexercised

`fieldWiring` confirmed at source: `resolvedId = id ?? name`, with the collision
ceiling documented in a comment. Nothing here contradicts the design; nothing
here confirms it either, because **the template has no form**. Their ten rules
(`.sankara-field*`) ship into every consumer's stylesheet regardless — about
480 bytes of CSS this site cannot use.

For a package whose 0.x exit is gated on a real consumer exercising the surface,
six of thirteen components having no consumer at all is the largest open item in
this report. It is a scope decision, not a defect: exercising them means a new
CMS-driven `form_section` blok, a Storyblok schema push and demo content.

**Decided 2026-08-13: the template does not add one.** A marketing-site template
has no form to model that would not be invented for the occasion, and inventing
one tests the blok, not the primitives. The `id ?? name` ceiling therefore stays
unobserved, and 0.x exit cannot claim the form surface has a consumer — the
first real form, in a project that actually needs one, is what closes this.

## Unobserved

Not measured, and not to be read as passing:

- **Dialog drawers.** `placement="end"` is where 0.9.0's rewrite is largest
  (`.sankara-dialog-end` now owns `inline-size`, `block-size`, `margin-inline`,
  `overflow-y`, and `.sankara-dialog-end.sankara-dialog-{sm,md,lg}` has to reset
  the centred `max-inline-size`). The template has no drawer. The specificity
  chain reads correct and the `max-inline-size: none` resets are present in the
  built CSS, but nothing rendered one.
- **`FaIcon`.** `.sankara-fa-icon` is in the built CSS; no element carries it.
- **`Icon`.** Not imported, so the narrowed `@source` above is verified by the
  presence of its two utilities in the output, not by a rendered icon.
- **Every other engine.** Chrome 151 only.
- **RTL.** `[dir='rtl']` drawer rules ship; the template is `de`.
- The 500px "narrow viewport" column is Chrome's minimum window width on macOS,
  not a phone. The clamp arithmetic checks out at that width; sub-400px is
  untested here.
